Task B

CI/CD for an OpenVMS product

Put an OpenVMS product under a CI pipeline that builds, tests and releases it on VMS/XDE, with the same tools you can install at your own site.

1 · Introduction and setup

Your team maintains ZeroMQ, a messaging library ported to OpenVMS. It is built by hand with @build.com and handed around as a PCSI kit. In this task you put it under CI: every push to the git server builds and tests it on OpenVMS, and a version tag publishes the PCSI kit.

Result
A pipeline that turns a tagged commit into a released PCSI kit, VSI-X86VMS-ZEROMQ-V0401-8A-1.PCSI$COMPRESSED.
Tools
Gitea (git server, pipelines, releases), gitea-runner (runs the pipeline jobs on VMS/XDE), tea (Gitea's command line), git, and xdecli (runs one DCL command on VMS/XDE from bash). All of them are installed and running in your container.
Repository
DKC200:[zeromq], on Linux /opt/xde/vms_os/V9.2/DKC200/zeromq: the team's existing git repository.

The pipeline grows by one stage per part:

build→test→kit→release

Each part starts from a prepared state and ends with a checkpoint: the result you should see. If you fall behind, the Task B page in VS Code sets the starting state of any part. Claude Code (right pane) can explain a log or a command at any time; nothing in this task requires it.

This task uses Claude Code in the pane on the right, as in Getting started. The terminal alternative: Getting started, G5.

B1 · Connect VMS/XDE as a CI runner

Gitea stores pipelines but does not run them. A runner fetches the jobs and executes them. Here the runner is gitea-runner in your container, so its jobs can call OpenVMS through xdecli.

  1. Write the runner's configuration. It tells gitea-runner which jobs it takes, how many at once, and where job folders go. Open the Explorer (top icon of the activity bar), right-click the folder Runner (/data/runner), choose New File…, name it config.yaml, paste the content below, and save with Ctrl+S.

    → →
    file · Runner/config.yaml
    runner:
  file: .runner          # registration, written by "gitea-runner register"
  capacity: 1            # one job at a time
  labels:
    - "xde:host"         # jobs with "runs-on: xde" run here, directly in the container
cache:
  enabled: false
host:
  workdir_parent: /opt/xde/vms_os/V9.2/DKC200/ci   # job folders on the DKC disk
    SettingWhy
    labels: xde:hostA job with runs-on: xde runs on this runner, directly in the container (host), not in a Docker image.
    capacity: 1One job at a time. VMS/XDE runs at most 30 OpenVMS processes in total, and jobs share the task disk.
    workdir_parentThe key setting: job folders are created on the task disk, so OpenVMS sees them as DKC200:[ci...]. A folder outside a DKC disk is invisible to OpenVMS.

    For all options and their defaults, gitea-runner config generate prints a complete annotated file — the usual starting point at your own site.

  2. Back in a bash terminal (VMS/XDE Lab icon → New bash terminal), get a registration token for the repository. how: Setup step 3 A runner needs it once, to identify itself to Gitea. The command stores the token in the shell variable TOKEN; jq extracts it from Gitea's JSON answer, so you don't have to copy it by hand.

    bash terminal
    TOKEN=$(tea api -X POST /repos/xdews/zeromq/actions/runners/registration-token | jq -r .token)
echo $TOKEN

  3. Register the runner with Gitea, from the runner's folder. --instance is Gitea's address inside the container; --name is how the runner appears in Gitea. The label comes from config.yaml.

    bash terminal
    cd /data/runner
gitea-runner register --config config.yaml --instance http://127.0.0.1:3330 --token "$TOKEN" --name xde --no-interactive

  4. Start the runner in the background. nohup … & keeps it running after the command returns and writes its messages to runner.log. On a real server this would be a systemd service; the commands are the same.

    bash terminal
    nohup gitea-runner daemon --config config.yaml >runner.log 2>&1 &

  5. OPTIONALWatch the runner's log: open a second terminal (VMS/XDE → New bash terminal) and follow the log there. how: Setup step 3 Keep this tab: in the next parts it shows each job the runner takes. Closing the tab stops only the viewer, not the runner.

    bash terminal (second tab)
    tail -f /data/runner/runner.log

  6. OPTIONALCheck the result. In VS Code the CI/CD view now shows runner running. In the Gitea tab, open the repository's Settings → Actions → Runners: the runner xde is Idle, waiting for jobs.

✓ Checkpoint — the runner log shows declare successfully, and the CI/CD view shows runner running.

B2a · First pipeline

You add the pipeline file to the repository. From now on every push builds ZeroMQ on OpenVMS, and the pipeline reports whether OpenVMS really succeeded.

  1. Create the pipeline file. Gitea reads pipelines from .gitea/workflows/ in the repository. In the Explorer, expand Task, right-click zeromq, choose New File…, type .gitea/workflows/ci.yaml (the folders are created with it), press Enter, paste and save. how: B1 step 1

    →
    file · zeromq/.gitea/workflows/ci.yaml
    name: ci

on:
  push:
  workflow_dispatch:

env:
  # our own run directory on the task disk (OpenVMS: DKC200:[ci.run_<n>])
  RUN_DIR: /opt/xde/vms_os/V9.2/DKC200/ci/run_${{ gitea.run_number }}

jobs:
  build:
    runs-on: xde
    steps:
      - name: checkout
        run: |
          rm -rf "$RUN_DIR"
          git clone --quiet http://127.0.0.1:3330/${{ gitea.repository }}.git "$RUN_DIR"
          git -C "$RUN_DIR" checkout --quiet ${{ gitea.sha }}
      - name: build
        run: |
          cd "$RUN_DIR"
          xdecli "@[.ci]run.com @build.com" | tee step.log
          grep -q 'CI-RESULT=OK' step.log
    PartWhat it does
    on: push, workflow_dispatchRun on every push, and on demand (used in the final QA run).
    env: RUN_DIROur own run folder on the task disk, DKC200:[ci.run_<n>]. The runner deletes its own job folder after each job; this one stays, so later jobs can share it.
    runs-on: xdeRun on the runner you registered in B1.
    checkoutPlain git clone of exactly the pushed commit — no ready-made "actions": they would be downloaded from GitHub.
    buildxdecli runs one DCL command on OpenVMS; its default directory is the current Linux directory, the run folder. The command runs the product's own @build.com through the wrapper below.

  2. Create the DCL wrapper ci/run.com the same way (right-click zeromq → New File… → ci/run.com). It is needed because xdecli always returns Unix status 0, whatever OpenVMS reports — a failed build would still look green. The wrapper runs the command, reads OpenVMS's own result $STATUS, and prints one line the pipeline step checks:

    file · zeromq/ci/run.com (DCL)
    $! [.ci]run.com - run one CI step on OpenVMS and report its real result
$! usage: @[.ci]run.com @build.com SRC 32   (P1 = command, P2.. = its parameters)
$ set noon                                 ! go on after an error: we report it
$ 'p1' 'p2' 'p3' 'p4' 'p5' 'p6' 'p7'
$ status = $status                         ! text, e.g. "%X00030001"
$ severity = f$integer(status) .and. 7     ! 0 warning, 1 success, 2 error, 3 info, 4 fatal
$ result = "FAIL"
$ if severity .eq. 0 .or. severity .eq. 1 .or. severity .eq. 3 then result = "OK"
$ write sys$output "CI-STATUS=''status' CI-RESULT=''result'"
$ exit 'status'
    LineWhy
    set noonDCL stops a procedure at the first error by default; the wrapper must go on to report it.
    'p1' 'p2' …Runs the command given as parameters, e.g. @build.com.
    status = $statusOpenVMS's result, a text like %X00030001.
    f$integer(status) .and. 7The severity: 0 warning, 1 success, 2 error, 3 information, 4 fatal. Warnings count as OK, as in the product's own build.
    CI-STATUS=… CI-RESULT=OK|FAILThe line the step looks for with grep -q 'CI-RESULT=OK'.

  3. Commit and push. git add selects the two new files, git commit records them, git push sends them to Gitea — which starts the pipeline.

    bash terminal
    cd /opt/xde/vms_os/V9.2/DKC200/zeromq
git add .gitea ci
git commit -m "Add first CI pipeline"
git push

  4. Watch the run. tea actions runs list shows the runs of the repository (--repo names it, because the local repository's address is the browser one, which tea does not match to its login); the runner's log tab from B1 shows it taking the job. The full build takes about 2 minutes.

    bash terminal
    tea actions runs list --repo xdews/zeromq

    When it has finished, show its result and jobs (runs list shows only whether a run is finished, runs view shows whether it succeeded):

    bash terminal
    tea actions runs view --repo xdews/zeromq 1

  5. Look at the run in the Gitea tab: repository → Actions lists the runs; click the run to see its Summary with the pipeline graph — one box per job. how: Setup step 6 It grows with each part.

✓ Checkpoint — tea actions runs view shows run 1 with Conclusion: success, and the graph shows the green job build.

B2b · Build jobs

You split the one build job into jobs, one per build stage. The pipeline graph then shows which stage failed, and the slow stages run only when they are needed.

The product's build.com already takes the stage as a parameter (prepared for this task), so each job runs one stage:

DCL commandBuilds
@build.com SRC 32the libraries and shareable images, 32-bit pointers
@build.com SRC 64the same, 64-bit pointers
@build.com TOOLSthe tool curve_keygen (links against the 32-bit build)
@build.com KITthe PCSI kit (needs both SRC builds)
checkout→compile-32→tools→kit ·checkout→compile-64→kit

  1. Open the pipeline file: in the Explorer, expand Task → zeromq → .gitea/workflows and click ci.yaml. Replace its whole content (Ctrl+A, paste) with the version below and save with Ctrl+S. how: B1 step 1

    file · zeromq/.gitea/workflows/ci.yaml
    name: ci

on:
  push:
  workflow_dispatch:

env:
  # our own run directory on the task disk (OpenVMS: DKC200:[ci.run_<n>]), shared by all jobs
  RUN_DIR: /opt/xde/vms_os/V9.2/DKC200/ci/run_${{ gitea.run_number }}

jobs:
  checkout:
    runs-on: xde
    steps:
      - name: clone
        run: |
          rm -rf "$RUN_DIR"
          git clone --quiet http://127.0.0.1:3330/${{ gitea.repository }}.git "$RUN_DIR"
          git -C "$RUN_DIR" checkout --quiet ${{ gitea.sha }}

  compile-32:
    needs: checkout
    runs-on: xde
    steps:
      - name: build.com SRC 32
        run: |
          cd "$RUN_DIR"
          xdecli "@[.ci]run.com @build.com SRC 32" | tee compile-32.log
          grep -q 'CI-RESULT=OK' compile-32.log

  # full build (64-bit, kit) only for tags and manual runs; pushes stay fast
  compile-64:
    needs: checkout
    if: startsWith(gitea.ref, 'refs/tags/') || gitea.event_name == 'workflow_dispatch'
    runs-on: xde
    steps:
      - name: build.com SRC 64
        run: |
          cd "$RUN_DIR"
          xdecli "@[.ci]run.com @build.com SRC 64" | tee compile-64.log
          grep -q 'CI-RESULT=OK' compile-64.log

  tools:
    needs: compile-32
    runs-on: xde
    steps:
      - name: build.com TOOLS
        run: |
          cd "$RUN_DIR"
          xdecli "@[.ci]run.com @build.com TOOLS" | tee tools.log
          grep -q 'CI-RESULT=OK' tools.log

  kit:
    needs: [compile-64, tools]
    if: startsWith(gitea.ref, 'refs/tags/') || gitea.event_name == 'workflow_dispatch'
    runs-on: xde
    steps:
      - name: build.com KIT
        run: |
          cd "$RUN_DIR"
          xdecli "@[.ci]run.com @build.com KIT" | tee kit.log
          grep -q 'CI-RESULT=OK' kit.log
    PartWhat it does
    jobs: checkout, compile-32, …One job per stage. Each job is a box in the pipeline graph and has its own log.
    needs:The jobs a job waits for. tools links against the 32-bit build, so it waits for compile-32; kit waits for both builds. A job whose needs failed does not run.
    if:The 64-bit build and the kit run only for tags (refs/tags/…) and manual runs (workflow_dispatch). A push builds and checks the 32-bit code only, and gets its answer sooner.
    RUN_DIR in every jobAll jobs work in the same run folder on the task disk: checkout clones once, the later jobs build in it. This works because all jobs run on the same runner, on the same OpenVMS disk.
    tee compile-32.logEach stage's output stays in the run folder under its own name, next to the build results.

  2. Commit and push. git commit -a records all changed files that git already knows, here ci.yaml, so no git add is needed.

    bash terminal
    cd /opt/xde/vms_os/V9.2/DKC200/zeromq
git commit -am "Split the build into jobs"
git push

  3. When the run has finished (about a minute; tea actions runs list --repo xdews/zeromq shows completed), show its jobs:

    bash terminal
    tea actions runs view --repo xdews/zeromq 2

  4. In the Gitea tab, open the run (Actions → the run). how: B2a step 5 The graph now shows the jobs and the needs lines between them. Click a job, for example compile-32, to see its log; it ends with the wrapper's CI-RESULT=OK line.

✓ Checkpoint — run 2 succeeded: checkout, compile-32 and tools are green, compile-64 and kit skipped.

B3 · Tests

You add a test job: after the build, the pipeline builds and runs ZeroMQ's own tests on OpenVMS. A push is green only if the code builds and the tests pass.

  1. OPTIONALLook at the prepared test scripts in zeromq/tests. You do not change them; the job only calls them, so you can skip to the next step. The folder holds about a hundred files, so open the test list with Quick Open: click into the VS Code window first (for example on the Explorer), so that the keys go to VS Code and not to the browser, which would open its Print dialog; then press Ctrl+P, type vms_tests.txt and choose the one in zeromq/tests (the others are copies in earlier run folders). The Explorer scrolls to the file; the two .com scripts are in the same folder.

    FileWhat it does
    vms_tests.txtThe tests to run, one name per line; ! starts a comment. It lists the tests that work on OpenVMS and do not need fixed TCP ports.
    build_tests.comCompiles and links each listed test against the 32-bit library [-.src]libzmq32.olb; prints N tests built.
    run_tests.comRuns each test, prints PASS name or FAIL name and the summary N passed, M failed; each test's own output goes to name.log. It exits with an error status if any test failed, so run.com reports CI-RESULT=FAIL.

  2. Add the test job: open .gitea/workflows/ci.yaml as in B2b, how: B2b step 1 go to the end of the file (Ctrl+End), paste the block below and save. Keep its two-space indent: test: belongs under jobs:, like kit: above it.

    file · zeromq/.gitea/workflows/ci.yaml (add at the end)
      test:

    runs-on: xde

          cd "$RUN_DIR"

          cd "$RUN_DIR"
          xdecli "@[.ci]run.com @[.tests]run_tests.com" | tee run-tests.log

    two stepsBuilding and running the tests are separate steps, so the log shows which of them failed. A step runs only if the steps before it succeeded.

B4 · Release

You add a release job. When you push a version tag, the pipeline runs every job, including the 64-bit build and the PCSI kit, and publishes the kit as a Gitea release. A push without a tag works as before.

  1. Give the release job a token. Creating a release needs a Gitea login, and a pipeline must not contain a password. So you create an access token and store it as a repository secret: Gitea hands it to the job and hides it in the logs. The command asks Gitea for a new token (curl with your login), extracts it (jq) and pipes it straight into the secret (--stdin), so the token never appears on the screen. The second command lists the repository's secrets: names only, never values.

    bash terminal
    curl -s -u xdews:lab -H 'Content-Type: application/json' \
  -d '{"name":"release","scopes":["write:repository","read:user"]}' \
  http://127.0.0.1:3330/api/v1/users/xdews/tokens \
  | jq -r .sha1 \
  | tea actions secrets create --repo xdews/zeromq --stdin RELEASE_TOKEN
tea actions secrets list --repo xdews/zeromq
    PartWhy
    "scopes"What the token may do: write:repository to create the release and upload the kit, read:user for tea to check the login. Nothing more.
    .sha1The field of Gitea's answer that holds the token. Gitea shows it only once, at creation.

  2. Add the release job at the end of .gitea/workflows/ci.yaml, as in B3 how: B3 step 2 (Ctrl+End, paste, save):

    file · zeromq/.gitea/workflows/ci.yaml (add at the end)
      release:
    needs: [test, kit]
    if: startsWith(gitea.ref, 'refs/tags/v')
    runs-on: xde
    steps:
      - name: publish the kit
        run: |
          cd "$RUN_DIR"
          # VMS file names: match case-insensitively
          kit=$(find . -maxdepth 1 -iname '*.pcsi$compressed' | head -1)
          # own tea login, apart from yours (the runner runs as your user);
          # removed after the step, as it holds the token
          export XDG_CONFIG_HOME=$(mktemp -d)
          trap 'rm -rf "$XDG_CONFIG_HOME"' EXIT
          tea login add --name ci --url http://127.0.0.1:3330 \
              --token "${{ secrets.RELEASE_TOKEN }}" >/dev/null
          tea releases create --login ci --repo ${{ gitea.repository }} \
              --tag "${{ gitea.ref_name }}" --title "ZeroMQ ${{ gitea.ref_name }}" \
              --asset "$kit"
    PartWhat it does
    needs: [test, kit]Publish only a kit whose code passed the tests.
    if: startsWith(gitea.ref, 'refs/tags/v')Only for version tags (v…). A push to master and the manual QA run never publish anything.
    find … -iname '*.pcsi$compressed'The kit that kit built in the run folder. OpenVMS file names come back in either case, so the match ignores case.
    XDG_CONFIG_HOME=$(mktemp -d), traptea keeps its logins in its configuration folder. The runner runs as your user, so without this the job's login would land among your own. The trap removes the temporary folder, and the token in it, when the step ends.
    ${{ secrets.RELEASE_TOKEN }}The secret from step 1; in the log it shows as ***.
    tea releases create … --assetCreates the release for the tag and attaches the kit.

  3. Commit and push, then tag the commit and push the tag. The push starts a normal run (release skipped); the tag starts the full run with the release. They run one after the other: the runner takes one job at a time.

    bash terminal
    cd /opt/xde/vms_os/V9.2/DKC200/zeromq
git commit -am "Add the release job"
git push
git tag v4.1.8-ws1
git push origin v4.1.8-ws1

  4. Both runs take about 3½ minutes together: about one for the push, two and a half for the tag. Then show the tag run (run 5):

    bash terminal
    tea actions runs view --repo xdews/zeromq 5

  5. Check the release: tea releases list shows it (-o simple: one line per release instead of a wide table), tea releases assets list its files, the PCSI kit.

    bash terminal
    tea releases list --repo xdews/zeromq -o simple
tea releases assets list --repo xdews/zeromq v4.1.8-ws1

    In the Gitea tab, the repository's Releases page shows the release with the kit to download. how: Setup step 6
